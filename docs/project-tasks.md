# FlowDesk 完整项目任务清单

更新日期：2026-10-14。目标是交付可部署、可演示、可解释设计取舍的多租户工单平台，作为全栈岗位的主项目。

仓库 `fullstack-engineering-lab` 是作品集容器；FlowDesk 是其中正在开发的产品。先把 FlowDesk 做完整，再按需要扩展独立项目。当前目录保持不变，新增其他项目时另行规划仓库布局。

## 状态与范围

- `[x]` 表示已有实现及验证记录；`[ ]` 表示待完成，不能提前写成简历成果。
- 第一阶段基础工程与 2A 认证已完成；独立真实 PostgreSQL 已验证迁移与约束，Compose 容器启动仍待补齐。
- 保留五个大阶段；阶段内按任务组分批执行，不一次完成所有功能。测试、文档和安全边界随功能一起交付。
- 必须完成第二至第五阶段的核心任务，才能将项目作为完整作品展示。AI、附件等属于增强项。
- 基础技术栈沿用当前 React、NestJS、Prisma、PostgreSQL 与 pnpm；实现时再核对实际版本和 API。

## 完整版本的业务闭环

用户注册或登录 → 创建/加入企业 → 选择企业 → 按角色创建与处理工单 → 留下评论和操作记录 → 查看真实统计 → 退出。

一个用户可加入多个企业，企业间的成员、工单、评论、审计和统计必须隔离。演示至少准备两个企业与不同角色，不能只验证一个账号的正常操作。

## 第二阶段：认证、组织与后端权限

### 2A：身份认证

- [x] P2-01：确定注册、登录、退出、当前用户与刷新会话的接口契约、错误码和 DTO。
- [x] P2-02：新增密码摘要与必要会话模型、迁移；规范化邮箱，处理重复注册，响应排除密码摘要。
- [x] P2-03：选择合适的密码摘要方案，实现注册与登录；无效凭据使用统一反馈，禁止日志记录密码或令牌。
- [x] P2-04：实现短期 JWT access token、过期验证和认证 Guard；密钥由环境配置并校验，不提供固定生产密钥。
- [x] P2-05：实现 refresh token 轮换、摘要存储、过期和退出撤销；明确旧令牌复用的处理规则。
- [x] P2-06：明确令牌传输方式。推荐 access token 保存在内存，refresh token 使用 HttpOnly Cookie；同步设计 Secure、SameSite、CORS 和必要的 CSRF 防护，不仅设置 Cookie 属性。
- [x] P2-07：前端接入真实登录、注册与当前用户；处理刷新后会话恢复、过期、退出和受保护页面。
- [x] P2-08：统一处理 401；并发请求只触发一次会话刷新，刷新失败停止重试并清理会话，避免循环请求。
- [x] P2-09：为注册、登录、退出、过期、刷新轮换和无凭据访问添加行为测试，补充真实数据库集成测试。

验收：可以从新账号完成登录、刷新页面和退出；未登录访问业务 API 返回 401；过期或已撤销会话不能恢复登录。浏览器密码和令牌不会出现在 URL、日志或业务响应中。

### 2B：企业组织与成员

- [ ] P2-10：实现创建企业与 OWNER Membership 的事务；失败时不能留下只有企业、没有所有者的半成品。
- [ ] P2-11：实现用户所在企业列表、企业详情、企业切换和企业基本信息修改。
- [ ] P2-12：确定成员状态与成员移除规则；记录保留策略，防止删除历史工单的作者身份。
- [ ] P2-13：实现成员列表与角色修改；分页参数有上限，联合唯一约束冲突转换为合适的 HTTP 响应。
- [ ] P2-14：实现企业邀请的创建、接受、撤销与过期。绑定目标身份，邀请令牌保存摘要，不允许任意账号冒领。
- [ ] P2-15：首版可由管理员复制邀请链接；邀请仅向授权角色展示，不写入日志。自动发邮件属于可选集成，不阻塞核心闭环。
- [ ] P2-16：保护最后一个 OWNER，处理两个请求同时降级/移除 OWNER 的并发情况；确定所有权转移规则。
- [ ] P2-17：前端接入企业选择、创建、成员管理与邀请页面，处理无企业、无权限和空列表状态。
- [ ] P2-18：企业切换时取消旧请求并清理/隔离缓存；TanStack Query 的租户查询 key 包含 organizationId。

验收：同一个用户可以在两个企业拥有不同角色；非成员不能访问企业；重复加入失败；邀请只能按规则接受；最后一个 OWNER 不会被并发操作移除。

### 2C：RBAC 与租户边界

- [ ] P2-19：先写角色权限矩阵，明确企业操作与工单操作的角色、资源范围和特殊条件。
- [ ] P2-20：建立后端租户上下文：认证用户 → 当前有效 Membership → 企业角色；客户端传入 organizationId 只表示访问意图。
- [ ] P2-21：实现权限声明与 Guard，Service 同时验证资源归属和业务条件；阻止用户通过注册/修改请求自赋 OWNER 或 ADMIN。
- [ ] P2-22：为所有企业业务读写施加租户条件，约定跨租户资源统一返回 404 或其他明确策略，避免泄漏资源存在性。
- [ ] P2-23：在真实数据库中创建企业 A/B 和四类角色，覆盖跨租户读取、修改、删除、角色篡改及已移除成员访问。
- [ ] P2-24：前端按权限呈现导航与按钮，并明确该行为不替代后端授权。

建议初始权限如下，具体接口实现前写入 permissions.md 并补充状态限制。

| 角色   | 企业与成员                       | 工单可见范围   | 工单操作                                         |
| ------ | -------------------------------- | -------------- | ------------------------------------------------ |
| OWNER  | 管理企业与成员，转移所有权       | 本企业全部     | 创建、指派、处理、关闭                           |
| ADMIN  | 管理非 OWNER 成员与常规配置      | 本企业全部     | 创建、指派、处理、关闭                           |
| AGENT  | 查看必要的企业信息与可指派成员   | 本企业全部工单 | 创建，处理分配给自己的工单；不能任意管理成员     |
| MEMBER | 查看自己的成员信息与必要企业信息 | 自己创建的工单 | 创建、补充评论，按状态规则确认关闭；不能自行指派 |

MEMBER 读取列表、详情、评论及统计都需应用相同资源范围，不能只对修改接口做权限检查。四角色首版使用固定矩阵，自定义角色与权限编辑器是增强项。

阶段交付：真实认证和企业成员页面、认证/邀请模型迁移、权限文档、接口文档、租户隔离与会话测试记录。

## 完整版本后的增强项

以下不是首版完成条件。每次只选择一个有产品用途的增强方向。

| 方向        | 可选任务                                     | 必须证明的能力                                                             |
| ----------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| AI 助手     | 工单摘要、分类建议、知识库检索与回答         | 后端调用模型，密钥隔离；知识库按租户检索；引用来源；超时、费用限制与评测集 |
| AI 数据安全 | 权限过滤、检索边界、提示注入测试与数据最小化 | A 企业内容不会出现在 B 企业回答中；模型不能越过后端授权或自动执行敏感操作  |
| 附件        | 上传、下载、类型/大小校验和私有存储          | 下载先验证工单权限；随机存储 key；未授权链接不可获取内容                   |
| 通知        | 站内通知、邮件、异步任务与失败重试           | 租户及接收者权限、幂等、可重试、不重复通知                                 |
| SLA         | 响应时限、超时标记与提醒                     | 明确工作时间、状态计算与重复执行规则                                       |
| 自定义权限  | 角色与细粒度授权编辑                         | 一套可靠的后端策略与回归测试，不只做配置表单                               |

AI 增强放在业务、租户隔离和部署稳定之后。先做辅助建议并由用户确认，不让模型直接修改角色、关闭工单或绕过权限。尚未实现的增强项不得出现在简历“已完成”列表中。

## 每批任务的执行与学习方式

1. 指定任务编号与边界，检查当前改动和依赖环境。
2. 先写接口/数据/权限规则与验收场景，再实现一条可验证流程。
3. 前后端一起联调，执行对应测试、lint、类型检查和构建；涉及数据库时实际应用迁移。
4. 更新文档、核对错误分支，保留可审查 Git 提交；需要同步时再上传 GitHub。
5. 你完成一次独立复现和代码讲解，再进入下一批。记录遇到的问题、原因及解决方式。

每个阶段至少能独立讲清一个设计：第二阶段讲身份与租户，第三阶段讲状态与事务，第四阶段讲测试与缓存，第五阶段讲部署与恢复。AI 产出的代码需要你能读懂并解释，不能只依赖展示页面。
